Props Are Not a Design System

A simple frontend guide to building consistent and scalable UI components using semantic variants, controlled modifiers, and well-defined component properties.

One-line summary: A design system should define reusable design decisions, not expose unlimited styling props for every component usage.

1. Main Idea

When building UI components, it is tempting to expose many styling properties such as color, font size, border radius, padding and margin.

But if every developer can change these values independently, the application can slowly become visually inconsistent.

The goal:

Move design decisions from individual component usage into reusable component definitions.

2. The Problem with Too Many Props

Consider a button component that accepts many visual properties.

❌ Too many styling props

<Button
  color="blue"
  radius="10px"
  fontSize="16px"
  padding="12px 20px"
  fontWeight="500"
>
  Save
</Button>

❌ Another usage

<Button
  color="blue"
  radius="6px"
  fontSize="18px"
  padding="14px 22px"
  fontWeight="600"
>
  Save
</Button>

Both buttons perform the same action, but their visual design is different.

When this happens throughout a large application, maintaining a consistent design becomes difficult.

3. What Does "Semantic" Mean?

Semantic means the name describes the meaning or purpose of the component, rather than describing its raw CSS properties.

❌ Property-based thinking

<Button
  background="blue"
  textColor="white"
  radius="8px"
>
  Save
</Button>

✅ Semantic thinking

<Button variant="primary">
  Save
</Button>

Primary has a meaning in the design system. The component itself decides what "primary" looks like.

Think:

"What is this component supposed to mean?"

Instead of:
"Which CSS properties should I manually set?"

4. What Are Variants?

A variant represents a predefined visual or behavioral version of a component. 

<Button variant="primary">
  Save
</Button>

<Button variant="secondary">
  Cancel
</Button>

<Button variant="danger">
  Delete
</Button>

Example

Variant Meaning Example Usage
primary Main action Save, Submit, Continue
secondary Alternative action Cancel, Back
danger Destructive action Delete, Remove
success Positive action/state Approve, Confirm

5. What Are Modifiers?

A modifier provides a controlled variation of a component without creating a completely different component. 

<Button
  variant="primary"
  size="small"
>
  Save
</Button>

<Button
  variant="primary"
  size="medium"
>
  Save
</Button>

<Button
  variant="primary"
  size="large"
>
  Save
</Button>

Here, variant defines the main design, while size provides a controlled variation.

6. What Properties Should a Component Have?

Component properties should be intentional. We should not expose every CSS property just because it is technically possible.

Property Type Examples Recommended?
Semantic variant="primary" ✅ Yes
Controlled variation size="large" ✅ Yes
State disabled, loading, active ✅ Yes
Content / behavior children, href, onClick ✅ Yes
Raw color color="#123456" ⚠️ Usually avoid
Raw spacing padding="17px" ⚠️ Usually avoid
Raw radius radius="13px" ⚠️ Usually avoid
Raw typography fontSize="19px" ⚠️ Usually avoid
Important:

This does not mean raw properties are always forbidden. They can be useful for genuinely flexible or low-level components. The important point is to avoid turning every component into a collection of unlimited styling controls.

8. Bad vs Good Component API

❌ Too much freedom

<Button
  color="blue"
  background="#0055ff"
  fontSize="18px"
  fontWeight="500"
  padding="15px"
  radius="12px"
  shadow="..."
>
  Submit
</Button>

✅ Controlled API

<Button
  variant="primary"
  size="large"
>
  Submit
</Button>
Key difference:

❌ The first example asks the developer to design the button.

✅ The second example asks the developer to choose an existing design.

9. React Example

A simple component API could look like this: 

function Button({
  variant = "primary",
  size = "medium",
  disabled = false,
  children
}) {
  return (
    <button
      className={
        `button button--${variant} button--${size}`
      }
      disabled={disabled}
    >
      {children}
    </button>
  );
}

Usage

<Button
  variant="primary"
  size="medium"
>
  Submit
</Button>


<Button
  variant="danger"
  size="small"
>
  Delete
</Button>


<Button
  variant="secondary"
  size="large"
  disabled
>
  Cancel
</Button>

10. Avoid Endless Overrides

If developers repeatedly override the same properties, it may indicate that the component API is missing a useful variant.

❌ Repeated overrides

<Button
  variant="primary"
  size="large"
  radius="xl"
  fontSize="xl"
  fontWeight="500"
>
  Buy
</Button>

✅ Meaningful variant

<Button variant="purchase">
  Buy
</Button>

The goal is not to create hundreds of variants. The goal is to identify meaningful and repeated design patterns.

11. Team Guidelines

  • Prefer semantic props such as variant="primary".
  • Use variants for predefined designs rather than individual CSS values.
  • Use modifiers for controlled variations such as size.
  • Keep component APIs small and intentional.
  • Avoid exposing every CSS property as a component prop.
  • Reduce one-off overrides that create visual inconsistency.
  • If the same override appears repeatedly, consider creating a variant.
  • Keep design decisions centralized so changes can be made in one place.

13. Final Summary

Don't make every component usage a design decision. Create the design once, name it semantically, and reuse it.

A design system is not about giving developers more CSS props. It is about giving developers the right choices.
